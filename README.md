# 自动旁路供电 (Bypass Charger)

> 让手机/平板在插着充电器时**停止给电池充电**，改由适配器直接供电。
> 降低边充边玩时的发热与电池损耗。

## 这是什么

小米系设备自带一个「夜间充电」（智慧充电保护）功能：夜里充电到一定电量就暂停，早上再充满。
它的本质是**暂停充电但不断电**——设备继续由适配器供电，电池既不充也不放。

这个模块就是接管那个开关，让你可以**自己决定在什么电量暂停充电**。

效果：

- 插着充电器打游戏 / 看视频，电池不再反复充放，发热明显降低
- 长期插电使用（当桌面设备），电池不会一直顶在 100% 高压状态，减缓老化
- 拔掉充电器后正常用电池，电量降到设定值以下会自动恢复充电

## 功能特性

| 特性 | 说明 |
|---|---|
| **旁路供电** | 电量达到阈值后停止充电，设备由适配器供电 |
| **双向阈值** | 到达「停止阈值」暂停充电，低于「恢复阈值」自动恢复，带滞回防抖动 |
| **精确模式（任意阈值）** | 机型有 `soc_limit` 节点时，**1–100% 任意阈值都能精确实现**，实测 95% 阈值停在 95% |
| **兼容模式** | 机型只有 `smart_night` 时走厂商夜间充电，阈值 80–100% 有效（厂商上限 80%） |
| **图形控制面板** | KsuWebUI 界面内实时看电量/电流/温度，直接开关和改阈值 |
| **改动即时生效** | 改完配置 1 秒内生效，无需重启、不用等巡检周期 |
| **跨机型自适应** | 自动探测控制节点路径，兼容不同厂商 sysfs 层级 |
| **单实例保证** | `mkdir` 原子锁，不会出现重复守护进程 |
| **写入校验** | 每次写配置都回读确认，失败明确报错而非静默失败 |
| **开机自启** | 等待系统就绪后自动拉起守护进程 |

## 兼容性

需要设备具备厂商的 `smart_charge` / `smart_night` sysfs 节点。**实测通过**：

| 设备 | 型号 | 系统 | Root 方案 | 模式 |
|---|---|---|---|---|
| 小米平板 7 Ultra | `25032RP42C` (jinghu) | Android 17 / HyperOS 4.0.0.13 | KernelSU 3.3.1 | 兼容模式（无 `soc_limit`） |
| 小米 17 | `25113PN0EC` (pudding) | Android 17 / HyperOS 4.0.5 | SukiSU Ultra 4.2.1 | **精确模式**（有 `soc_limit`） |
| Redmi K60 Pro | `22127RK46C` (socrates) | Android 15 / HyperOS 3 | KernelSU | 兼容模式（节点 `qcom-battery/night_charging`） |

**注意：不同机型路径层级和节点名都不一样**，模块已做自动探测，覆盖三种情况：

- 新平台：`platform/.../smart_charge/smart_night`
- 老 MIUI：`qcom-battery/night_charging`（如 K60 Pro）

如果你的机型节点名字不一样，可以手动确认：

```bash
su -c 'find /sys/devices -maxdepth 8 \( -name "smart_night" -o -name "night_charging" \)'
```

只要这条命令有输出，模块基本就能用。没有输出则说明该机型没有这个功能。

是否具备精确模式，看同级目录下有没有 `soc_limit`：

```bash
su -c 'ls /sys/devices/platform/*/smart_charge/ /sys/devices/platform/*/*/smart_charge/ 2>/dev/null | grep soc_limit'
```

有输出 → 精确模式，阈值 1–100% 全支持；无输出 → 兼容模式，最低 80%。

要求：已取得 root，root 方案可以是 **KernelSU**、**SukiSU Ultra** / 其他 KernelSU 分支、
**Magisk** 或 **APatch**。两代 KernelSU 的 WebUI 接口签名不同，模块已做自适应。

## 安装

1. 下载 Release 中的 `bypass-charger-v10.1.0.zip`
2. 打开 KernelSU / Magisk 管理器 → **模块** → **从本地安装**
3. 选择 zip → 安装完成 → **重启设备**

重启后模块会自动启动，默认在 **80% 停止充电 / 75% 恢复充电**。

## 实现原理

### 核心思路

厂商的「夜间充电」功能在底层对应一个 sysfs 节点：

```
/sys/devices/platform/.../smart_charge/smart_night
```

- 写入 `1` → 暂停充电（进入旁路）
- 写入 `0` → 恢复充电

模块不去改充电电流、也不去碰电池保护逻辑，**只是替你把那个开关按下去**。所以：
充电曲线的安全性、温度保护、JEITA 逻辑等全部仍由厂商固件负责，模块本身不改动任何充电参数。

### 为什么这算「真旁路」

用库仑计（`charge_counter`）实测，`smart_night=1` 时：

```
charge_counter  Δ = 0        # 电池既没充进去也没放出来
current_now     -101000 µA → +33000 µA   # 由流入电池变为停止
写回 0 后        → -45000 µA              # 立刻恢复充电
```

`Δ=0` 是关键证据：如果只是「停止充电」，设备运行仍会消耗电池电量（`Δ` 为负）；
而实测 `Δ=0` 说明系统确实把供电切换到了适配器，电池处于静置状态。

### 两种控制模式（重要）

厂商其实提供了两个层级的节点，能力差别很大：

**① `smart_night` —— 只是个开关**

它**不是**「立刻停止充电」，而是**「开启厂商夜间充电模式」**：

```
写入 1  →  厂商进入夜间充电模式："充到 80% 就停"
         ├─ 当前电量 < 80%：继续充电，直到 80% 才停（你的阈值被忽略）
         └─ 当前电量 ≥ 80%：立刻停止充电（看起来像"你的阈值生效了"）
```

所以只靠它，阈值最低只能到 80%。

**② `soc_limit` —— 真正的充电上限**

这是厂商的充电上限值，实测可以直接控制：

```
写 100，当前 90%  →  立刻 2.4A 充电
写 90， 当前 94%  →  5 秒内停充
写入后长时间无人改写
```

**模块优先使用 `soc_limit`（精确模式），没有该节点时才退回 `smart_night`（兼容模式）。**

| 模式 | 判定条件 | 阈值范围 | 实测 |
|---|---|---|---|
| 精确模式 | 同级目录存在 `soc_limit` | **1–100%** | 阈值 95% → 充到 95% 精确停止 |
| 兼容模式 | 只有 `smart_night` | 80–100% | 低于 80% 一律按 80% 执行 |

精确模式的实现方式：电量达到阈值时把 `soc_limit` 压到「阈值 − 1」（小于当前电量即触发停充），
低于恢复阈值时放开为 100。**状态直接编码在 `soc_limit` 里，不依赖额外的状态机。**

另外，精确模式会**强制把 `smart_night` 保持为 0** —— 一旦为 1，厂商会按它自己的 80% 上限介入，
反过来把 `soc_limit` 抢回 80，导致我们的设置失效。

### 已排查的其他节点

为寻找控制点，以下节点也实测过，结论供后来者参考：

| 节点 | 可写 | 有效 | 说明 |
|---|---|---|---|
| `battery/charge_control_limit` | 是 | ❌ | 哑属性。写 16 命令成功，回读恒为 0 |
| `battery/charge_control_limit_max` | — | — | 值是 16，不是百分比，说明这是厂商的哑实现 |
| `smart_charge/smart_ichg` | 是 | ❌ | 值能存（写 100 回读 100），但充电电流纹丝不动 |
| `smart_charge/batt_safe_lvl` | 是 | ❌ | 写 75 回读 0，直接被拒 |
| `platform/soc_limit/`（平板） | — | ❌ | 只是个未绑定的空设备（`waiting_for_supplier`），无可用属性 |

所以只有带 `soc_limit` 文件的机型才能进精确模式；平板上并不存在这个文件，
`/sys/devices/platform/soc_limit` 那个同名目录是干扰项，不是控制点。

`smart_night` 在夜间充电被激活时，守值是厂商 HAL 服务
**`vendor.xiaomi.hardware.batteryantiaging-service`**。所以精确模式要避开它 ——
不让 `smart_night` 变成 1，它就不会介入。

### 守护进程工作流

```
开机 → service.sh 等待 boot_completed + 10s
     → 探测控制节点（缓存 / 通配 / find 三级）
     → 获取 mkdir 单实例锁
     → 进入主循环：
          读 config.sh
          读 capacity（当前电量）
          判定 desired：
              capacity >= 停止阈值          → 1（开旁路）
              capacity <= 恢复阈值          → 0（恢复充电）
              其余（滞回区）                → 保持原状态
          desired 与当前节点值不同 → 写入并记日志
          可被 SIGUSR1 打断的等待（CHECK_INTERVAL）
```

### 几个关键设计

**1. 节点路径自动探测**

各机型 sysfs 层级不统一（有的在 `platform/smart_charge`，有的在
`platform/soc/soc:smart_charge`），写死路径必然翻车。采用三级策略：

```sh
1. 读 node.path 缓存（存在且有效直接用，避免轮询时反复搜索）
2. 通配匹配 platform/*/smart_night、platform/*/*/smart_night
   + 旧版 battery/night_charging
3. 兜底 find /sys/devices -maxdepth 7 -name smart_night
```

**2. 单实例锁**

原版用 PID 文件判断，但 `$$` 在 `{ ... } &` 子 shell 中返回的是**父进程** PID，
父进程早已退出，判断永远失效 → 每次启动叠加一个僵尸实例。改用 `mkdir` 的原子性：

```sh
mkdir "$LOCK_DIR" 2>/dev/null || { 检查持有者是否存活，僵死则回收 }
```

**3. 滞回与重新裁决**

单纯比较 `capacity >= 阈值` 会在阈值附近反复开关。引入恢复阈值形成滞回区。
但同时带来一个问题：把停止阈值调高到当前电量之上时，会卡在滞回区不恢复充电。
因此**检测到阈值变更时，按当前电量重新裁决一次**（不走滞回）。

**4. SIGUSR1 即时唤醒**

原先改完配置要等满一个巡检周期（间隔设 120 秒时就是两分钟），看起来像「设置无效」。
现在等待改为后台 `sleep` + `wait`，`webui.sh set` 写完后发 `SIGUSR1` 打断等待：

```sh
nap() {
  sleep "$CHECK_INTERVAL" &
  SLEEP_PID=$!
  wait "$SLEEP_PID" 2>/dev/null
}
```

**5. WebUI 单行协议**

KernelSU 的 `ksu.exec(cmd)` 同步接口**只回传最后一行输出**。最初用多行 KV 输出，
前端只能拿到最后一行，表现为「电量 0% / 阈值 undefined」。

现在后端所有命令都只输出**一行**，用 `;` 分隔 KV；日志里的换行转义为字面量 `\n`，
前端再还原。

另外，KernelSU 是把原生 Java 对象用 `addJavascriptInterface` **直接暴露**成 `window.ksu`
的，没有 JS 包装层，所以参数必须是 String。前端做了三种签名自适应探测：

```java
String exec(String cmd);                                    // 同步返回 stdout
void   exec(String cmd, String optionsJson, String cbName); // 异步，回调是函数名
void   exec(String cmd, String cbName);
```

**6. 写入回读校验**

配置写入后立刻回读比对，不一致就放开权限重试，仍失败则返回 `ERR=write_failed`，
前端明确提示，而不是假装成功。

## 参数说明

配置文件：`/data/adb/modules/bypass_charger/config.sh`

| 参数 | 默认 | 范围 | 说明 |
|---|---|---|---|
| `ENABLED` | `1` | 0 / 1 | 模块总开关。设 0 立即恢复充电，守护进程保持运行 |
| `ENABLE_THRESHOLD` | `80` | 1–100 | 停止充电阈值。电量 ≥ 此值 → 暂停充电。精确模式全范围有效；兼容模式低于 80 会按 80 执行 |
| `DISABLE_THRESHOLD` | `75` | 1–100 | 恢复充电阈值。电量 ≤ 此值 → 恢复充电 |
| `CHECK_INTERVAL` | `15` | 5–600 | 电量巡检间隔（秒）。**改配置不受此限制，恒为即时生效** |

约束：`DISABLE_THRESHOLD` 必须**低于** `ENABLE_THRESHOLD`，且至少相差 5%。
不满足时后端会自动把恢复阈值压到「停止阈值 − 5」。

**关于巡检间隔**：它只影响对**电量变化**的检测频率。设得太大（如 120 秒），
电量到阈值后可能还会继续充一会儿、冲过 1–2%，导致实际停止点偏高。建议 15–30 秒。

## 常见问题

**Q：系统弹出「智慧充电保护：电量达 80% 已暂停充电，将在 06:00 恢复充电」？**

正常现象，这正是模块生效的表现。模块接管的就是厂商的夜间充电开关，系统检测到开关被打开，
就按它自己的逻辑播报了这条通知。

- 不影响旁路，不会撤销模块的设置
- 就算系统在 06:00 真的恢复了充电，守护进程下一轮巡检也会立刻压回去
- **别点那条通知里的「立即充满」**，点了就是主动取消旁路
- 嫌烦可以在通知设置里关掉该通知渠道，不影响功能

**Q：阈值能设多低？会被系统限制吗？**

**看机型。** 取决于系统里有没有 `soc_limit` 节点，模块自动判断：

- **有 `soc_limit`（精确模式）**：1–100% 全部有效。实测阈值设 95%，电量充到 95% 精确停止。
- **只有 `smart_night`（兼容模式）**：最低 80%。低于 80% 会按 80% 执行并在日志提示。

原因是这两个节点的语义完全不同，详见上文「两种控制模式」。

精确模式实测：

| 操作 | 结果 |
|---|---|
| 电量 94% 时把上限写 100 | 立刻 2.4A 充电 |
| 阈值 95%、电量充到 95% | 精确停住，日志 `停充（上限 94%）` |
| 电量 94% 时把上限写 90 | 5 秒内停充 |

兼容模式实测（阈值低于 80 无效）：

| 场景 | 结果 |
|---|---|
| 电量 93% → 写 `smart_night=1` | 立刻停止充电 |
| 电量 51% → 阈值设 50 | **无效**，电流仍为 4.4A，一路充到 80% |

**Q：会不会伤电池 / 不安全？**

模块不改任何充电参数（电流、电压、温度保护全部交给固件）。它只是替你按下厂商已有的
「暂停充电」开关，安全性等同于你手动在设置里开启夜间充电。

**Q：我的机型不支持怎么办？**

```bash
su -c 'find /sys/devices -maxdepth 7 -name "smart_night"'
```

有输出 → 提 issue 附上路径，可以适配；无输出 → 该机型没有这个功能。

**Q：WebUI 显示「连接失败」/ 读取失败？**

不同版本 KernelSU 的 `ksu.exec` 方法签名不一致。前端已内置三种签名自适应探测。
若仍失败，请提供 logcat：

```bash
adb logcat -s bypass_webui
```

**Q：怎么卸载？**

管理器里移除模块 → 重启。卸载后节点恢复默认值 `0`（即正常充电），不留残留。

**Q：拔掉充电器后有影响吗？**

没有。节点只影响「插着电时是否给电池充电」，拔掉后完全由系统正常管理。

  不再让人设了 70% 却发现实际按 80% 执行。提示文案也会说明当前模式。
- **修正**：脚本头部版本号与 `module.prop` 不一致。
- **修正**：`customize.sh` 缺失（不影响运行，仅安装时使用）。

### v10.1.0

**新增精确模式：突破 80% 下限，任意阈值 1–100% 都能精确实现。**

- **新增**：自动探测 `soc_limit` 节点。有该节点时直接控制充电上限，
  不再依赖厂商夜间充电，因此阈值不再受 80% 限制。实测阈值 95% → 充到 95% 精确停止。
- **修复**：关闭模块后充电不恢复。原先只写 `smart_night=0`，但厂商的 `soc_limit`
  仍卡着，导致电量 ≥80% 时插电也不充。现在关闭时会同时把上限放开为 100%。
- **修复**：精确模式下修改阈值后卡在滞回区不重新裁决。
- **新增**：`status` 输出 `MODE=precise|compat`，WebUI 可据此提示可用阈值范围。
- **兼容**：没有 `soc_limit` 的机型（如小米平板 7 Ultra）自动退回原模式，行为不变。

### v10.0.3

- **调整**：模块 `author` 改为作者酷安名，原版信息移至 `description`。功能无变化。

### v10.0.2

- **修复**：拔掉充电器后未清除旁路标记，导致电量在「恢复阈值~停止阈值」区间内掉下来时
  状态仍保留为开；下次插电会因为仍在滞回死区内而保持旁路，**插着电却一直不充电**，
  且插电后电量不掉、永远出不去。现在断开电源即清零，插电后按当前电量重新裁决。
- **修正**：停止阈值下限改为 **80%**。实测证明低于 80% 不会生效 ——
  `smart_night` 实为「开启厂商夜间充电」开关，厂商固定充到 80% 才停。
  低于 80% 的配置会在日志中提示并按 80% 执行，WebUI 拒绝保存低于 80 的值。
- **文档**：补充节点真实语义说明与实测数据。

### v10.0

针对 Android 17 / HyperOS 4 的重构，相对原版 v9.9：

- **修复**：控制节点路径变更导致模块完全失效（新系统节点迁移至 `smart_charge/smart_night`）
- **修复**：PID 守卫失效导致每次启动叠加僵尸实例，改用 `mkdir` 原子锁
- **修复**：相同阈值（如 80/80）会在同一点反复开关，改为强制 5% 滞回
- **修复**：阈值调高到当前电量之上后卡在滞回区不恢复充电
- **修复**：配置写入失败仍返回成功，改为回读校验
- **新增**：控制节点三级自动探测，兼容不同 sysfs 层级
- **新增**：KsuWebUI 控制面板（状态显示 / 开关 / 阈值 / 日志）
- **新增**：SIGUSR1 唤醒，改配置 1 秒内生效
- **新增**：单行输出协议，适配 `ksu.exec` 只回传一行的限制
